# ADR-021 · 常驻解析进程（`nlsh --serve`）

- 状态：已采纳
- 日期：2026-10-25
- 相关：ADR-015（设备分档）、ADR-020、change `nl-shell-runtime`

## 背景

规则层命中时一次调用 0.04s / 7.6MB（见 ADR/CHANGELOG 的惰性加载条目）。规则未命中要加载
428MB 模型：实测 **1.8s 加载 + 780MB 常驻**，每次调用都重付一遍。终端钩子上线后这个代价
变成"每条听不懂的句子都付一次"，交互体验直接崩。

STATE 里"模型常驻进程"这条待决策一直挂着，钩子把它顶到了必须回答的位置。

## 决策

`nlsh --serve` 常驻，一条 unix socket，行分隔 JSON，单线程。

- **路径**：`$XDG_RUNTIME_DIR/nl-os/parse.sock`（无 XDG 则 `/tmp/nl-os-<uid>/`），目录 0700、socket 0600。
- **惰性加载**：守护进程启动时只 `nl_init_lazy()`，**第一条请求**才真加载模型。
- **空闲卸载**：`--idle`（默认 300s）无请求 → `nl_free()` 归还内存；`--max-idle`（默认 3600s）后进程退出。
- **自动拉起**：客户端连不上时 `fork` 两次拉起（双 fork，中间进程立即退出，守护进程被 init 收养），
  最多等 5s；**只在 stdin 是 TTY 时**这么做（脚本/测试/管道不偷偷养常驻进程）。
- **三级回退**：本地规则（免费） → 常驻进程 → 进程内加载（老行为）。任何一级失败都退到下一级，
  **绝不因为 IPC 失败让命令失败**。
- **`--no-model` 语义保持**：既不加载模型，也不问守护进程（否则等于偷偷用了模型）。

## 协议

```
请求：  {"v":1,"input":"进入 /tmp 目录"}\n
响应：  {"ok":true,"intent":5,"command":"cd /tmp","perm":1,"confirm":0,
         "source":0,"conf":1.0,"paths":["/tmp"],"slots":[{"n":"location","v":"/tmp"}],"debug":"..."}
        或 {"ok":false,"error":"无法解析"}
```

## 实测（2 vCPU）

| 场景 | 结果 |
|---|---|
| 第 1 次请求（含模型加载） | 23.7s |
| 第 2 次请求（复用模型） | 21.9s，守护 RSS 稳定在 **796MB**（没有重载） |
| 客户端进程 | 常驻 26MB（模型不在客户端进程里了） |
| 非 TTY 调用 | 不拉起、无 socket、走本地回退 |

**诚实的结论**：常驻省掉的是**加载**（约 1.8s/次）和 780MB 的反复分配，但**省不掉推理**——
单次推理本身要 20s 量级（128 token 生成 × 最多 3 次重试），这是模型层的既有瓶颈
（STATE「决策层延迟」）。守护进程让"第二次以及之后"不再付加载成本，但规则未命中的句子
整体仍然慢，须由模型/候选集那条线解决。

## 后果

- 客户端超时必须 > 单次推理耗时，否则白扔：定为 120s（先于本次实现的 20s 会整段丢弃）。
- 单线程足够：请求是"一问一答 + 秒级"，并发两个客户端时后者排队。
- 守护进程崩溃/未拉起时行为与升级前完全一致（走进程内加载）。
