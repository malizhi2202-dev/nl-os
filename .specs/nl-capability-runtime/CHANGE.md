# CHANGE: NL-OS 能力运行时 —— 端侧机器刚部署就能自己熟悉并安全执行

- **Change ID**: `nl-capability-runtime`
- **创建日期**: 2026-10-25
- **路径建议**: 完整（本次只交付 Phase 1；Phase 2/3 另开 change）
- **状态**: draft

---

## Why（为什么做）

一期 MVP（`nl-os`）已经把"自然语言 → 一条命令"跑通了（四层管线 + L1–L4 权限 + `.tools`），但它有两个结构性缺口，导致"端侧机器刚部署就能自己用"这个目标并不成立：

1. **机器不知道自己有什么能力。** 现在所有可执行能力都是硬编码在规则库和模板里的（`rules_db.h` / `templates_db.h`）。换一台机器（NAS 没有 `docker`、路由器没有 `systemctl`、工控机没有 `apt`），这份硬编码清单就是错的——用户说"重启 nginx"，模型不知道这台机器上根本没有 nginx。
2. **"解析的度"没有可证明的边界。** 复杂指令现在只有"模型猜"和"规则不命中"两种结果，既不能明确拒绝，也无法解释为什么拒绝。用户要的是：**超出能力就直说解析不了，并给出能做的替代步骤**，而不是硬猜一个错命令。

同时，第 4 点"要做决策"在原设计里被规划成 Agent Loop（Planner/Executor/Observer，ADR-008）。经外部核查（Jev 的 System One 接口），**不需要 Agent Loop**：决策可以收敛成"有限答案空间内的类型化判断"，从结构上就不可能乱解析。这条认知改变需要在本 change 定案，否则二期会沿着错误方向铺代码。

## What（做什么）

### 本次交付 · Phase 1：能力层（零模型依赖）

一句话：**让机器先知道"我能做什么"，再让自然语言来挑。**

- **能力自发现**：启动/`--scan` 时扫描本机可执行能力（PATH 中的二进制、systemd 单元、容器运行时、包管理器、`/proc` 与系统信息），产出能力清单
- **能力自检**：对发现的能力做只读自检（`--version` / `--help` 探测），分"可用 / 需特权 / 缺失"三档
- **能力注册表**：能力清单 + 每项的建议权限等级（L1–L4）+ 槽位描述，落盘为本地索引，支持增量重扫
- **快路径**：直接输入的传统命令、C 代码片段、已注册的函数调用包**不经模型**直接走规则层执行（延续现有"透传"行为，但显式化并纳入审计）
- **复杂度预算（规则版）**：对输入做结构化判定（跨几个能力？需要循环/条件？需要特权？超出注册能力？），超阈值直接返回"解析不了 + 可执行的替代步骤"
- **审计留痕**：每次 NL→动作记录能力 ID、权限等级、是否走快路径、拒绝原因

### 后续 phase（本次不交付，仅锁定方向，防止架构走偏）

- **Phase 2 决策层**：把 Layer 3 从"模型生成 JSON"改为类型化判断三原语——**Choice**（从能力注册表里选）/ **Score**（复杂度与风险打分）/ **Noul**（执行前是/否关卡），本地小模型 + 约束解码，输出只有几个 token
- **Phase 3 固化与可回滚**：一次成功的 NL 操作可固化为 `.tools`（下次不经模型）；L2/L3 操作自动留快照可撤销

## 想法压测（0-change 步骤 1.5）

- **技法**：假设反转 + 逆向 + 类比迁移
- **假设反转**：「必须先有强模型才能自然语言操作系统」→ 反转后成立：**能力清单是确定的，模型只需要做排序**，0.5B 够用，甚至无模型也能跑快路径
- **逆向**（怎么把它做到最糟）：能力清单靠硬编码 → 换机器全错；解析失败时猜一个命令 → 误删；决策交给模型自由生成计划 → 不可审计。这三条正好对应本 change 的三项核心设计
- **类比迁移**：Jev 的 State + 类型化问题 + 代码持有政策 —— 直接借它的接口形态（不用它的云服务），把 Layer 3 变成决策层
- **压测 6 问结论**：最不需要这个的是"只有一台固定开发机的重度用户"（他们记命令比说话快）；预算砍一半就只保能力自发现 + 快路径；最小可验证版本 = 能力清单 + 一次自检报告

## 架构层影响声明（0.4 选项 2 强制）

> `.specs/ARCHITECTURE.md` 尚不存在。以下冲击点必须在 2-design 落成正式 ADR，否则后续 change 会在不自洽的架构上开工。

| 冲击对象 | 影响 |
|---|---|
| **ADR-001 四层管线** | Layer 3 的定位从"模型推理生成 JSON"改为"类型化判断（Phase 2）"；Phase 1 不触碰 Layer 3，只扩 Layer 1/2 的边界 |
| **ADR-007 模块边界** | 新增项目级模块「能力注册表」（建议 `libnlc/capability_*.c` + 本地索引文件），需定义与其他模块的接口，不得由 `nlsh` 私自持有 |
| **ADR-008 Agent 架构** | **原 Planner/Executor/Observer 预留接口不再实现**；决策改为"有限答案空间内的类型化判断"，需新 ADR 记录这次推翻 |
| **ADR-003 `.tools`** | 固化（Phase 3）依赖能力 ID 稳定，`.tools` 格式需要增加能力引用字段 |
| **新增 ADR（2-design 落盘）** | ADR-012 能力注册表与能力自发现；ADR-013 类型化决策层（Choice/Score/Noul）替代 Agent Loop |

## 范围排除（这次不做）

- ❌ **Phase 2 决策层**（Choice/Score/Noul、约束解码）—— 另开 change
- ❌ **Phase 3 技能固化、回滚快照** —— 另开 change

- ❌ **GUI / 语音 / 多用户** —— 沿用 `nl-os` 的 out 清单

## 验收线（粗粒度）

1. 在一台新机器上首次运行，能自动产出一份能力清单 + 自检报告（可用/需特权/缺失三档），且不产生任何写操作
2. 20 条中文指令中，规则层可覆盖的部分生成正确命令且 L1–L4 判定正确；规则层覆盖不到的明确返回"解析不了 + 替代步骤"，不猜
3. 危险操作（路径穿越、零宽字符、间接引用保护路径）**0 漏网**，每次拦截都有审计记录
4. 同一份能力清单在 ARM64 与 x86_64 上有一致的结构与权限分级

## 风险与未知

| 风险 | 等级 | 处理 |
|---|---|---|
| 能力自发现扫描范围过大导致启动慢 | 🟡 中 | 增量索引 + `--scan` 显式触发；首次扫描有进度输出 |
| 不同发行版的 `--help` 格式差异导致自检误判 | 🟡 中 | 自检只做"能否执行/退出码"判定，不解析 help 文本语义（语义留 Phase 2） |
| 能力清单被污染（PATH 里有恶意同名二进制） | 🔴 高 | 只扫描白名单目录 + 记录绝对路径与 inode；不信任 PATH 顺序；执行前再次 realpath 校验 |
| 与现有 `rules_db.h` 硬编码清单重叠，出现双份真相 | 🟡 中 | 明确单一真相：注册表为主，规则库只引用能力 ID（2-design 定） |
| "解析不了" 的阈值定得太松/太紧 | 🟡 中 | 阈值必须是可配置常量并在 benchmark 上回归，不允许写死在代码分支里 |
