# LESSONS — 跨 change 失败教训库（常驻，不归档）

> 只在**踩过坑并已修**之后追加；每条给可复现的症状与正确做法。

## 2026-10-25 · vendor cJSON 是 API 子集，不是上游

**症状**：编译报 `implicit declaration of function 'cJSON_GetObjectItemCaseSensitive'`；
或运行期 `cJSON_GetArraySize(obj)` 对**对象**恒返回 0，导致递归遍历永远进不去。

**根因**：`third_party/cJSON/` 是自实现的兼容子集（25 个符号）：
- 没有 `cJSON_GetObjectItemCaseSensitive`，只能 `cJSON_GetObjectItem`
- 没有 `item->valuestring` 直连的推荐用法，应走 `cJSON_GetStringValue/GetNumberValue`
- **`cJSON_GetArraySize` 对 object 返回 0**（只对 array 有效）

**正确做法**：
1. 写 cJSON 代码前先 `grep '^cJSON' third_party/cJSON/cJSON.h`
2. 需要遍历 object/array 的子节点时，手动走 `node->child` / `it->next`（结构体字段是公开的）

**代价**：`verdict.c` 的路径扫描曾因此完全失效（`/etc/passwd` 未被拦截），
由 T04 的"保护路径必须 deny"测试抓出。**这类漏洞靠代码审查很难发现，必须有断言。**

## 2026-10-25 · `-Werror=format-truncation` 会连撞多轮

**症状**：`snprintf(dst, sizeof(dst), "%s", src)` 被 GCC 判为可能截断，`-Werror` 编译失败。

**正确做法**：变长字符串进定长缓冲，一律写精度说明符（`"%.127s"`），并单独处理"NUL 也要有位置"。
不要用 `-Wno-format-truncation` 关掉——超长文件名/ID 被静默截断是**数据正确性问题**（两个不同能力可能撞成同一个 ID）。

## 2026-10-25 · 测试通过 ≠ 测试有效

**症状**：`capability_scan` 的"不可读目录"用例一直通过，但什么都没测到。

**根因**：用 `mkdir(path, 0700)` 构造"不可读目录"——**属主自己依然可读**（root 更是）。

**正确做法**：不可读用 `0000`，且 `geteuid()==0` 时显式打印 `SKIP`，不要假装通过。
同理：任何"权限/存在性"类断言，先问一句"这个测试在什么条件下会真的失败"。

## 2026-10-25 · 端侧真实下沿是 512MB，不是 4GB

扫地机器人 SoC（全志 Cortex-A7 四核 + 512MB DDR3 + 4GB eMMC）是"能跑 Linux 的最小现实样本"。
0.35B decoder 常驻约 250MB，在这类机器上会 OOM → A1 档只能上 25MB 的 embedding。
**设计任何"端侧常驻内存"预算时，用 512MB 而不是 4GB 兜底。**

## 2026-10-25 · 只在 Release 才报的 `-Werror=unused-result`

**症状**：Debug 构建全绿，第一次 `-DCMAKE_BUILD_TYPE=Release` 构建失败：
`ignoring return value of 'write' declared with attribute 'warn_unused_result'`。

**根因**：Release 默认启用 `_FORTIFY_SOURCE`，`write`/`read` 等被标记 `warn_unused_result`；
`(void)write(...)` 不能消除该属性告警。

**正确做法**：消费返回值（`if (write(...) < 0) { /* ignore */ }`）。
**推广**：任何"只在 Debug 跑"的项目，交付前必须跑一次 Release 构建——否则会集中爆雷。

## 2026-10-25 · 失败响应必须先渲染 error

**症状**：`https` 拒绝返回 `{"ok":false,"result":{"alternatives":[...]}}`——**错误码消失**。

**根因**：`nl_cip_render` 先判 `payload` 非空就输出 `ok:false + result`，而 `error` 只在
"无 payload 的失败"分支里写。于是所有"拒绝但附替代方案"的响应都丢错误码。

**正确做法**：渲染顺序 = **先判 `!ok`**（带/不带 payload 两分支），再判 `ok + payload`。
**推广**：任何"状态 + 附加数据"的序列化，先处理异常态。

## 2026-10-25 · 实现了但没接线 ≈ 没实现

**症状**：ticket 限速 `nl_ticket_rate_ok()` 写好了、也有单测，但**从没有调用点**；
ADR 里承诺的 DoS 缓解实际不生效。

**根因**：单元测试直接调这个函数 → 通过；但端到端路径没接。

**正确做法**：安全类断言必须打在**端到端路径**上（`verify_all.sh` 连发 120 次 invoke，
断言出现 `E_POLICY_DENY`）。单测只能证明"函数对"，不能证明"系统在用"。

## 2026-10-25 · 审计/日志截断要丢最旧的，不是最新的

**症状**：`audit` 查询返回的最老记录，新写入的事件（含刚发生的拒绝）看不到。

**根因**：按行顺序填充到缓冲区，超长时截断尾部。

**正确做法**：环形保留"最近 N 条"，字节不足时**从最旧开始丢弃**。
排障场景要的是"刚刚发生了什么"。

## 2026-10-25 · 规则槽位 `after_key` 会吃进句尾修饰词（**已修复，附回归**）

**症状**：`查看 README.md 文件` → 目标被抽成 `README.md 文件`；`创建一个叫 demo 的文件夹` → `demo 的文件夹`。
生成命令变成 `cat README.md 文件` / `mkdir -p demo 的文件夹`，**必然失败**。

**根因**：`extract_after_key_long()` 取"关键词之后到句尾"，不剥中文修饰后缀，也不剥引号。

**修法**（`rule_engine.c`）：
1. 后缀表分两类——"结构词"（`的文件夹`/`的目录`/`的文件`/`的内容`）直接剥；
   名词类（`文件夹`/`目录`/`文件`/`内容`/`下`/`里`/`中`）**只在其前面是空白时才剥**，
   否则 `删除 旧文件` 会被啃成 `旧`。
2. 组合形式（`目录下`/`文件夹里`）必须排在单字前面，否则 `logs 目录下` 永远匹配不到。
3. 前导量词（`一个`/`叫`/`叫做`/`名为`）也去掉：`建一个 logs 文件夹` → `logs`。

**回归**：`tests/unit/rule_slot_test.c` 6 组 27 条断言，**同时测"该剥的剥"和"不该剥的别剥"**。
改这个函数前先跑它——它被大量规则共用。

## 2026-10-25 · 敏感路径清单要按"路径段"匹配，不是按字面

**症状**：敏感清单写 `/.ssh/`，实际路径是相对 `.ssh` 或以 `.ssh` 结尾 → 判不出来，**私钥被快照进磁盘**。

**正确做法**：把清单存成目录名（`.ssh`），匹配时检查 `/name/`、结尾 `/name`、以及整体等于 `name`。
**推广**：任何"路径黑名单"都不要假设调用方传的是绝对路径且带尾斜杠。

## 2026-10-25 · 快照/备份必须存绝对路径

**症状**：快照 manifest 存了相对路径，`--undo` 在另一个 cwd 执行时"成功"但文件没回来。

**正确做法**：落盘前 `realpath` 绝对化；恢复时不再依赖 cwd。

## 2026-10-25 · 测试里的 `(1024u*1024u)` 宏会静默溢出到 32 位

**症状**：`nl_tier_from_bytes(12u * 1024 * MB)` 传进去的不是 12GB，而是 12884901888 截断成 32 位后的值，
档位判定断言 `B must allow decoder` 直接失败——而产品代码是对的，错的是测试。

**根因**：宏 `#define MB (1024u * 1024u)` 的类型是 `unsigned int`，整个表达式在 32 位里算完再转 `size_t`。

**正确做法**：容量宏一律带类型 `#define MB ((size_t)1024 * 1024)`；跨 4GB 的算术不要依赖提升规则。
**推广**：任何"字节数/偏移量"的测试常量都写成 `(size_t)N * MB`。

## 2026-10-25 · 评估决策层必须同时报"分母"，否则会得出 100% 的假象

**症状**：候选收缩在真实注册表（1890 条）上非常窄，多数输入只有 **1 个候选**（平均 0.85）。
如果只报"模型在候选中选对了"的比例，会得到 98.5% 这种漂亮数字，
但真正的问题在上一层：100 条可判定输入里有 **33 条的正确能力根本没进候选**（漏救 33%）。

**正确做法**：评估输出必须拆成四段分母：`可判定条数` → `粗筛命中` → `给出选择` → `选择正确`；
另报"平均候选数"。模型选得再准，粗筛召回不上去，整体准确率就上不去。
**推广**：凡是"多阶段漏斗"的指标，都要报告每一级的通过数，不要只报末级比值。

## 2026-10-25 · 测量延迟必须连带记录宿主，否则数字不可用

**症状**：0.5B q4_0 单次受约束解码在本机要 2.5s（P95 5.0s），远超 ADR-015 的 B 档目标 1.5s；
换到正常 8 核机器上是几百毫秒量级。根因是 **2 vCPU + 负载 4.8 + 只剩 300MB 空闲内存**，
428MB 模型反复换页。

**正确做法**：延迟结论必须写明 CPU 核数/型号/负载/内存余量；否则不要写"达标/未达标"，
只能写"在本宿主上测得 X"。
**顺带**：`n_threads` 不要用库默认值，按 `sysconf(_SC_NPROCESSORS_ONLN)` 设（上限 8），少核机器上默认值会过订阅。

## 2026-10-25 · 给下载脚本"加校验"时把已下好的模型删了

**症状**：为修 `download_model.sh`"失败仍退出 0"的问题，加了 `curl --fail` + 校验 + 失败即 `rm -f "$FILE"`。
在已有完整文件上验证时，`-C -` 续传得到 **HTTP 416** → `--fail` 判失败 → 把 428MB 已经下好的模型删了。

**根因**：先写校验、后想幂等。`-C -`（断点续传）对**已完整**的文件本来就返回 416，
作者把 416 当成失败；而"失败即删除"直接毁掉好文件。

**正确做法**：
1. 幂等判断放最前：文件存在且 `head -c 4 == GGUF` 且体积合理 → 直接返回，**根本不联网**
2. 下载到 `$FILE.part`，校验通过后再 `mv`，**永远不要先删正式文件**
3. 校验脚本要在"已经成功"的状态下也跑一遍（幂等路径），不能只测失败路径
**推广**：任何"失败即清理"的操作，都要先确认被清理的对象不是有效产物。

## 2026-10-25 · Release 构建坏了很久没人发现（验证链只编一个 target）

**症状**：Debug（`-O0`）全绿、`ctest 28/28` 全绿，但 `cmake -DCMAKE_BUILD_TYPE=Release` 直接编译失败：
`snapshot.c` 两处 `-Werror=format-truncation`、`capability_scan_test.c` 的 `symlink` 未用返回值、
`adapter_http_test.c` 两处 `freopen` 未用返回值。

**根因**：`verify_all.sh` 只有在"AC-10 资源测量"那一步才建 Release，而且只 `make nlbroker`——
`nlbroker` 不包含 `snapshot.c`，也不包含测试目标。于是**发布配置从来没有被完整编译过**。

**正确做法**：
1. 验证脚本必须构建**全部 target** 的 Release（`cmake --build <dir>` 不带 target 名）
2. `-Wformat-truncation` / `-Wunused-result` 是 **`-O2` 才触发**的警告，Debug 里看不到；
   凡是"Debug 绿 = 能发布"的推断都不成立
3. 修法沿用既有约定：`snprintf` 用精度限定符（`%.4000s`）、系统调用返回值必须消费

## 2026-10-25 · 决策层的"召回"和"选择"是两个问题，先修前者

**数据**（120 条中文集，100 条可判定）：

| 阶段 | 修前 | 修后 |
|---|---|---|
| 粗筛命中（正确能力进候选） | 67 | **86** |
| 漏救率 | 33% | **14%** |
| 平均候选数 | 0.85 | 1.06 |
| 规则 top-1（命中集内） | 91.0% | **98.8%** |
| 受约束 Choice（命中集内） | 98.5% | 96.5%（强制解码时）/ 98.8%（规则有把握就不问模型） |

**关键教训**：模型在候选集内一直很准（96–98%），但**候选集本身错/空**时它无能为力；
而候选收缩用的是词典而不是规则引擎，导致"能执行的说法决策层选不出来"。
把规则层意图作为强提示（+50）并入候选收缩后，召回从 67% 跳到 86%，收益远大于换模型。

**推广**：多阶段漏斗先测每一级通过率，再决定优化哪一级；不要因为"末级指标好看"就以为系统没问题。

## 2026-10-25 · 改完才发现：`nlsh` 根本不执行自然语言解析出来的命令

**症状**：`nlsh -c '创建一个叫 uat 的文件夹'` 输出 `[create_dir] mkdir -p uat` + `需确认: 是`，
但**目录没有被创建**；同一条命令走 `nl-run`（`.tools`）才真的执行。
传统命令（`ls -la`、`cat /etc/hostname`）走快路径会执行，所以早期测试都"绿"。

**根因**：`dispatch.c` 在模板填充后只打印命令与确认标志，没有"确认 → 权限 → 快照 → 执行 → 审计"的后半段；
而 DESIGN §2 的管线图把这段画进去了。

**教训**：
1. 验收脚本要断言**副作用**（文件是否真的出现），不能只断言"打印了正确的命令"；
2. 管线图里画了的步骤，必须有对应 AC，否则"设计有、实现无"会静默存在很久。

## 2026-10-25 · 「生成命令是干净的」不等于「输入是干净的」

**症状**：`nlsh -c '创建一个叫 x; touch hacked'` 真的创建了 `hacked`；而命令级 guard
（`nl_exec_has_metachars(r.command)`）判定通过——因为生成的命令是 `touch hacked`，一个元字符都没有。

**根因**：规则层把用户输入里的尾巴当成独立命令解析掉了，注入发生在**解析前**，
防线却只设在**执行前**。

**正确做法**：
1. 不可信输入要在**入口**校验（NL 路径拒绝 `; | & $ ` > <`），执行前再校验一次生成命令
2. 写安全断言时必须测"副作用是否发生"，不能只看返回码或输出文本
3. 只读快路径（用户自己敲 shell）与 NL 路径是两套语义，别用同一套 guard 兜底

**代价**：这条是在写验收脚本时为 AC-8 编的用例撞出来的，差点以"已有命令级 guard"结案。

## 2026-10-25 · 词表式拒绝必须配反向守卫

**症状**：给预算层加"多动作/无能力操作"维度后，担心误伤 `清理 /tmp 目录` 这类正常句子。

**做法**：`budget_test` 同时写 5 条"必须拒绝"与 6 条"必须放行"，并跑 120 条评测集比对
改动前后的 `ok/refused/accuracy`——**数字完全一致**才算没误伤。

**教训**：拒绝规则的回归成本不对称（误伤会把能用的说法挡掉，且用户不会报 bug，只会不用），
所以正例比反例更值钱。

## 2026-10-25 · 阈值型测试要确认「代码真的走到了阈值」

**症状**：`NL_DECIDE_MIN_CONF=1.0` 时仍输出 `choice-llm`，测试失败。原因是**单候选**时
`nl_choose_with_model` 走"规则已确定、不问模型"的短路，压根没解码，闸门无从生效。

**正确做法**：
1. 测阈值/概率这类分支，先确认短路路径没被提前命中（本例用 `NL_DECIDE_SOLO_DECODE=1` 强制解码）
2. 方法名要反映真实路径：没解码就别叫 `choice-llm`（已改 `rule-decisive`）

## 2026-10-25 · 解析出来的元数据，要检查所有「写回」路径

**症状**：ADR-019 写着 `# @perm: allow-l2` 收窄为"只豁免 L2"，AC-11c 也"通过"了。但真跑
`nl-run --freeze x.tools && nl-run x.tools`（最常见用法），L2 仍然被问——策略头在固化时丢了。

**原因**：解析器把 `# @perm:` 提进 `s->allow_l2`；固化函数只写 `# @format` + `# @checksum` +
正文，**没有把策略头写回去**。读取侧验证一百遍也发现不了，因为丢的是写回路径。

**为什么旧断言没抓到**：AC-11c 验的是"L3 仍然要确认"——属于负向用例，缺陷（策略头全丢）
和非缺陷（只收窄到 L2）都会让它通过。补上正向用例 AC-11i（allow-l2 真的豁免 L2）才判得出。

**做法**：策略头写进固化文件并纳入校验和（改头 = 篡改），正向/负向用例成对存在。

**教训**：凡是"解析时提取、其它地方消费"的元数据（权限、格式、开关、编码），列一遍它的
**所有**去路（固化/导出/复制/重写/缓存），逐条验证；只测消费者等于没测。

## 2026-10-25 · 启动时 eager 加载大件资源，等于给每条命令加税

**症状**：用户说"占用 CPU 很大，很快就满了"。查下来不是执行慢，是 `nlsh` 启动就 `nl_init()` 加载
428MB 模型——**连"创建一个叫 X 的文件夹"这种规则层一句话就能决定的命令也要付**：3.57s、779MB、
2.1s CPU（2 vCPU 上打满一核）。

**判据**：同一句 `--no-model` 只要 0.22s / 18MB。差 20 倍不是算法问题，是加载时机问题。

**做法**：懒加载到真正需要的那一层（Layer 3 `ensure_model()`）；未命中才加载。
修复后 0.16–0.34s / 19MB，规则未命中的句子照旧加载，行为不变。

**教训**：凡"启动时加载"的大件（模型/索引/词典/树），先问一句"这次调用真的会用到它吗"；
把加载推迟到消费点，比优化消费点本身的收益大一个量级。测成本要拿"不需要它的那条路径"做对照。

## 2026-10-25 · 优化做完了，用户还在跑旧二进制

**症状**：惰性加载已经实测 0.16–0.34s / 19MB，用户却继续反馈"占用 CPU 很大"。
再测 `~/.local/bin/nlsh`：**1.2–2.9s / 675MB**——装的是 22:37 的构建，而含惰性加载的构建是 22:44。
源码改了、测试过了、提交了，**但没 `install_local.sh`**，用户路径上跑的还是旧程序。

**判据**：测成本必须测**用户实际执行的那个路径**（这里 `~/.local/bin/nlsh`），
只测 `build/` 下的产物会把"没部署"误判成"优化无效"，或者反过来把优化记成已完成。

**做法**：`bash scripts/install_local.sh` 重装后复测：规则命中 0.04s / 7.6MB，
规则未命中 1.9s / 677MB（`--no-model` 报"无法理解"，证明是真未命中，加载是对的）。

**教训**：无 CI、靠本地安装交付的项目，**build ≠ install**。验收清单里固化一条：
"用户实际执行路径上的产物时间戳/体积是否已更新"；否则每一条性能结论都只对 `build/` 成立。

## 2026-10-25 · 断言了"加载了"没断言"成功了"，一条每次调用都崩的路径活了很久

**症状**：`nlsh -c '显示当前工作目录'`（规则未命中，要走模型）每次都以
`GGML_ASSERT(n_tokens_all <= cparams.n_batch) failed` 退出，`rc=134`。
原因是 decode 分块按 `n_ctx`(512) 切，而断言要求 `n_tokens_all <= n_batch`(256)，
一段 300 token 的 few-shot prompt 直接 abort。

**为什么长期没被发现**：AC-14 断言的是"规则未命中 → 加载模型 → RSS 涨到 786MB"，
**没有断言解析成功**。进程拿到 786MB 后立刻 abort，RSS 指标却完全符合预期，测试因此一直是绿的。
我自己也踩了同一个坑：第一次量到"1.9s / 677MB"就当成成功了，实际那是崩溃前的资源峰值。

**判据**：看一个慢/重操作是否"成功"，要看**退出码或产物**，不能只看资源指标；
`/usr/bin/time` 的 `%e/%M` 在崩溃时照样有值。

**做法**：分块上限改用 `llama_n_batch(ctx)`；验收里补"解析后进程存活且退出码 ≠ 134"。

**教训**：性能断言（RSS/耗时）只能证明"干了活"，不能证明"干成了"。
凡是测试里出现"资源涨了就算通过"，都要再补一条**结果断言**——否则它保护的是一条会崩的路径。

## 2026-10-25 · 钩子里 cd 不生效：`command_not_found_handle` 跑在子 shell

**症状**：钩子在 `command_not_found_handle` 里执行 `cd /tmp`，返回码 0，但父 shell 的 `PWD` 不变。

**判据**：`command_not_found_handle(){ cd /tmp; }; nosuchcmd; pwd` —— 一条命令就能自证。

**做法**：把"改变 shell 状态"这件事交给**主 shell 里跑的东西**（`PROMPT_COMMAND`）：
子 shell 只写指令文件，主 shell 读文件执行 `cd -- "$dir"`（只传路径，不 eval）。

## 2026-10-25 · 阈值改松是最糟的"修测试"，先问前提是不是变了

**症状**：加了决策层兜底后，`AC-14 规则未命中：真加载模型（RSS > 300MB）` 变红，
实测 RSS 只有 19MB。

**差点走错的路**：把阈值从 300MB 调低、或者干脆删掉这条断言——那样"模型路径真的会加载"
就再也没人守着了。

**真实原因**：断言的前提变了。它用的例子 `显示当前工作目录` 现在由**决策层**兜底、
本来就不该加载模型——是**测试需要换例子**，不是阈值需要放松。

**做法**：换一个真正会走到模型层的句子（`总结一下这个目录是干什么用的`，815MB / 29.6s），
同时把新行为单独锁成 `AC-15`（兜底 pwd 不加载模型 + 高危不兜底）。

**教训**：断言失败先分类：①实现错了 ②前提变了 ③断言本身没测到点上。
只有①才改实现；②要换输入/换场景**并把前提变化记录下来**；改阈值属于③的下下策——
它会让一条本来能抓 bug 的防线永久失效。

## 2026-10-26 · 抽样不等于覆盖：我一直用"想得到的几种说法"当测试

**症状**：用户一句「当前工作路径」既没被规则层也没被决策层接住，落进模型层并卡死。
而我此前所有验证都是挑 10 来句"我觉得常见"的话各试一遍。

**本质错误**：那是**抽样**，不是**覆盖**。抽样集的元素是我自己写的，
天然覆盖不到"用户第一句话就会说的那个说法"，而且永远不知道自己漏了什么。

**做法**：改成**语义簇 + 改写不变性**测试 —— `tests/paraphrase/nl-paraphrase-zh.json`：
同一能力下 10–17 种说法（书面/口语/疑问/带礼貌词/同义替换/中英混/省略），
断言**全簇必须落到同一个命令**。`scripts/verify_paraphrase.py` 输出逐簇通过率和**具体失败的说法**。

**关键补充**：调完词典后又建了**留出集**（`-holdout.json`，调参时没看过）。
结果是调参集 100% / 留出集 **84%** —— 这个差值就是过拟合的真实大小。
不建留出集，就会拿"我自己写的句子全过"当"中文说法都支持"。

**教训**：凡是要断言"能听懂一类输入"，先问一句"我这个测试集是谁写的"。
自己写的集合只能证明**没退化**，不能证明**能泛化**；留出集才能。

## 2026-10-26 · `template_id == 0` 是通配符：给某个 intent 加模板会静默改变别的规则

**症状**：新增 lsof 模板后，「怎么样」「磁盘情况怎么样」整句变成 `lsof -i -P -n`。

**根因**：模板查找的条件是 `(template_id == 0 || TEMPLATES[i].template_id == template_id)`，
且循环以 `template_id != 0` 终止 —— 也就是 **`template_id == 0` 的语义是"该 intent 的第一个模板"**。
规则 122（`{"怎么"} → NL_INTENT_OTHER, tmpl 0`）此前因为 OTHER 意图下没有模板而落空，
我把 lsof 模板挂到 OTHER 之后，它立刻"有了"模板。

**教训**：`0` 当通配符的 API，加数据就等于改语义。新模板挂到语义正确的既有意图
（`SHOW_PROCESS`），并把这条约束写进模板表注释与 ADR-023。

## 2026-10-26 · 后台进程：`waitpid` 等错了对象 = 用户终端无限挂起

**症状**：`nlsh -c 当前工作路径` 卡在 `do_wait` **2 分 21 秒**仍未返回，子进程是
`nlsh --serve`（状态 `do_poll`，说明它并没有在推理，只是活着）。

**根因**：`spawn_daemon()` 单 fork 后父进程 `waitpid(pid)`，而那个子进程 exec 成了常驻守护进程
—— **守护进程活多久，用户终端就卡多久**，且没有超时。

**为什么长期没发现**：之前所有验证都是"先手动 `--serve &` 起好再测客户端"，
`ensure_running()` 的探测分支直接返回，**spawn 分支从来没被走到过**。

**做法**：双 fork（中间进程 setsid 后立刻退出）+ 回归测试直接断言"返回耗时 < 500ms"
（`tests/unit/spawn_detached_test.c`，用 `sleep 2` 做靶子：旧实现必等满 2 秒）。

**教训**：①"在我这儿能用"经常意味着某条分支没被走过；测的时候要问"这条路我刚才真的走了吗"。
②任何 `wait` 都要能说出"我在等谁、它多久会结束"；等一个设计上永不结束的进程就是无限期挂起。

## 2026-10-26 · 用户报一句、我补一条规则 = 穷举，不是覆盖

**症状**：用户报「解析www.baidu.com这个域名的dns」「网卡信息」都"无法理解"，
我一比一加了两条规则 + 两张模板。用户当场点破：**「这不就成了穷举了吗 没有通用的处理吗」**

**根因**：规则是**整句形态**匹配。用户换语序、加"帮我"、换同义词，规则就不命中，
所以规则库再大，命中率都等于"我碰巧见过多少种说法"。这不是实现缺陷，是**方法错**。

**做法**：把信号分层 —— 规则只当高频缓存；"在问哪一类东西"交给决策层（提示词→候选能力）；
"参数是什么"交给**结构化抽取 + 形状校验**（域名：`nl_domain_check`）；模型层只在候选内做受约束选择。
判断"这句话在问远端名字还是本机"是**结构性**的（句中有没有合法域名），写进关键词规则只会两头不讨好。

**怎么验证"是不是真通用"**：写一批**没参与调参**的说法跑一次，跑完即作废。
本次三批：34/35 → 20/23 → 19/19，中间两次失败暴露的都是**类级**缺陷
（大小写敏感、1-2 字虚词提示词撞车、证据权重不够），而不是"少背了一句话"。
没有留出集，这三类缺陷只会表现为"用户下次又报一句"。

## 2026-10-26 · 权限表改了却"没生效"：注册表是缓存，不是真相

**症状**：把 `ip`/`dig` 从 L4 登记成 L1 后，决策层仍然一个候选都不出。

**根因**：权限等级被**扫描时落盘**进注册表，而 `--scan` 只"新增"、从不刷新已有条目的 `perm`。
于是表改了、老机器上永远是旧结论，用户也不可能想到"改完表要重扫"。

**做法**：装载时对 `source == "scan"` 的条目按权限表重新取值（人工 `--allow` 的不覆盖）；
注册表为空时 `nlsh` 自己扫一次并落盘 —— **通用层必须开箱可用**，不能靠用户先知道某个命令。

**教训**：任何"缓存了策略结论"的落盘数据，都要能回答"策略变了它怎么跟上"。

## 2026-10-26 · few-shot 示例把上下文窗口撑爆，模型层报"没有内存槽"

**症状**：一条本该走模型的句子 23 秒后"无法理解"，stderr 出现
`failed to find a memory slot for batch of size 1`。

**根因**：给 prompt 加了两个 few-shot 示例后，prompt 约 500 token，而 `n_ctx` 是 512
—— prompt 塞得进去，**却没有位置生成**，`llama_decode` 在 KV 满时报错。

**做法**：`n_ctx = 2048`（0.5B/2 KV heads 的 KV 约 12KB/token ≈ 25MB），生成循环按 `pos < n_ctx` 停。

**教训**：改 prompt 等于改资源需求。上下文窗口预算要按"prompt + 最长输出"算，不是只算 prompt。
